# SH-2 JIT Milestone 2E - Background Compiles and Decoded-Block Reuse Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move native compiling off the emulation thread and stop re-decoding returning code, so the x64 JIT is faster than the interpreter on every title, without stutter, while staying lockstep-exact. Then measure against the 2E bar, and profile the generated code if a title is still at or below 1.0.

**Architecture:** A native compile splits into three phases:
- `Prepare`: the emulation thread runs the emitter into an asmjit `x86::Compiler`. This is where every read of emulator state, including the page table, happens.
- `Finalize`: a worker thread runs asmjit's passes and serialization. It reads only objects owned by the prepared compile, never emulator or backend state.
- `Commit`: the emulation thread adds the code to the runtime, then installs and publishes it.

Because of that split, the worker cannot race the emulator, and a flush, reset or dropped block only has to discard results; no code needs to be freed. One `CompileWorker` thread is shared by both CPUs and owned by `CoreWrapper`. With no worker (the option is off, too few cores, or tests), compiles are synchronous as today. Track E adds a retired pool for IR-only blocks, next to 2D A1's native pool.

**Tech Stack:** C++20 (`std::thread`, `std::mutex`, `std::condition_variable`, `std::atomic`), CMake 3.28+, asmjit (vendored), Catch2, MSVC 2022 / GCC 14 / Apple Clang; ThreadSanitizer on Linux CI.

**Spec:** `design/sh2-jit-m2e.md`. **Evidence:** `design/sh2-x64-performance.md` ("Milestone 2D track A results"). **Code:** `src/jit/src/block_cache.cpp`, `src/jit/src/executor.cpp`, `src/jit/src/x64/x64_backend.cpp`, `src/bridge/core_wrapper.cpp`.

## Global Constraints

- **Exactness:** with the JIT on, either backend, with or without the worker, emulation is identical to the interpreter at every `Advance()` return; the only accepted deviations are `design/sh2-jit.md` section 6.5. Lockstep is the oracle. *When* native code becomes available may vary between runs; *what* is emulated may not.
- **Thread boundary:** only `PreparedCompile::Finalize` runs on the worker. It must not read the block, the context, the bus, guest memory, the backend's runtime, its link table or any `BlockCache` state. `Prepare`, `Commit`, publishing, installing, releasing and `Reset` run on the emulation thread, outside any running block (the 2D track A code-lifetime rules).
- **No data races:** the JIT tests run under ThreadSanitizer on Linux CI (Task 4). A TSan report is a bug.
- **Shutdown:** destroying a `BlockCache` (executor destruction, backend switch, JIT disabled, core unload) cancels its queued jobs and waits for its job in flight; no worker result is delivered to a destroyed cache. Destroying the `CompileWorker` joins its thread. No hang, no use-after-free (issue #7 was a crash on Close Content).
- **Synchronous mode:** with `worker == nullptr` everything behaves exactly as at the base commit. Every existing test keeps passing unchanged in that mode, and tests construct caches and executors without a worker unless they test the worker.
- **Memory:** native code cap 128 MB per CPU (`kMaxNativeCodeBytes`) and IR cap (`kMaxCachedInsts`) unchanged. Retired IR blocks (Task 5) count toward the IR cap. Prepared compiles waiting in the queue are bounded (`kMaxPendingCompiles`).
- **Both backends:** the IR backend has no native compiles and never uses the worker. Task 5 applies to both backends.
- **Fork scope:** `src/core/{include,src}/ymir/hw/sh2/*` and the read-only accessor in `ymir/sys/bus.hpp`; edits marked `// Brimir:` and logged in `src/core/BRIMIR_FORK.md`. This plan should need none.
- **Includes:** `brimir-jit` includes only `ymir/core/types.hpp`, `ymir/hw/sh2/sh2_jit_iface.hpp` and `ymir/hw/sh2/sh2_decode.hpp` from the core; asmjit only under `src/jit/src/x64/`.
- **Portability:** everything builds and passes without x64 (macOS ARM64 CI, Raspberry Pi 3). The worker is only enabled on x86-64 builds (ARM64's core gate is milestone 3).
- **Tests:** Catch2 in `tests/unit/`, JIT tests tagged `[jit]`, worker tests also `[worker]`. Never weaken an assertion.
- **Workflow:** branch `feature/sh2-jit-2e` from `master`; commit messages `type(scope): subject`; never stage `ROADMAP.md`, BIOS/ROM, `.chd` or `.smpc` files. Push the branch for CI before Task 6's report.

## Review Focus

1. **A compile in flight across a flush, reset or state-load flush:** its result belongs to an older generation of the cache and must be dropped, never committed, even if a block with the same PC was built since. Test in Task 3.
2. **A block dropped (stale) while its compile is in flight, and a new block built at the same PC before the result arrives:** the result must not be installed into the new block. Test in Task 3.
3. **A page remapped between `Prepare` and the commit:** the committed block's prologue compares the arrays seen at `Prepare` and reports stale on its first run; the executor rebuilds it and the "freshly compiled block reported stale" assert does not fire. Test in Task 3.
4. **The executor destroyed while its job is being finalized** (backend switch, JIT toggled, core unload): no crash, no hang, no result delivered afterwards, and the other CPU's jobs unaffected. Tests in Tasks 2 and 4.
5. **IR pool reuse after a page changes from an array page to a handler page with the same bytes:** the block's `fetchFromArrays` and known refills would differ from a fresh build, so it must not be reused. Test in Task 5.

**Interfaces:**
- Produces, in `backend.hpp`:

  - `virtual std::unique_ptr<PreparedCompile> INativeBackend::Prepare(const Block &block, const ymir::sh2::SH2JitContext &ctx) = 0;` runs on the emulation thread. It returns nullptr where `Compile` would fail before asmjit work (`CanEmitBlock`, offsets, `EmitBlock` failure).

Before calling `m_runtime->add`, `Commit` reads nothing the worker could still be writing.

### Task 2: CompileWorker

**Files:**
- Create: `src/jit/include/brimir/jit/compile_worker.hpp`, `src/jit/src/compile_worker.cpp`
- Modify: `src/jit/CMakeLists.txt`
- Test: `tests/unit/test_jit_worker.cpp` (new; add to the test target the way the other `test_jit_*.cpp` are)

**Interfaces:**
- Consumes: `PreparedCompile` (Task 1).
- Produces, in `brimir::jit`:
  - `struct CompileJob { const void *owner; uint64_t ticket; std::unique_ptr<PreparedCompile> prepared; };`
  - `struct CompileResult { uint64_t ticket; std::unique_ptr<PreparedCompile> prepared; bool ok; };`
- `class CompileWorker` (non-copyable). The constructor starts one thread; the destructor drops queued jobs, waits for the job in flight and joins. Methods:
  - `void Submit(CompileJob job)`: FIFO.
  - `void TakeResults(const void *owner, std::vector<CompileResult> &out)`: appends this owner's finished results in completion order.
  - `bool HasResults(const void *owner) const`: no lock taken when there are none. A per-owner atomic count or an equivalent is the builder's choice; the cache calls it on every `Get` that has compiles pending.
  - `void Cancel(const void *owner)`: drops the owner's queued jobs and undelivered results, and returns only after the owner's job in flight, if any, has finished. Results of that job are dropped.
  - `uint64_t BusyNs() const`: worker time spent in `Finalize`, since construction.
  - `size_t Pending(const void *owner) const`: queued plus in flight.
- The worker never calls into the owner. It only runs `prepared->Finalize()` and parks the result.

### Task 3: Background compiles in the block cache

**Files:**
- Modify: `src/jit/include/brimir/jit/block_cache.hpp`, `src/jit/src/block_cache.cpp` (`Hit`, `Get`, `Build`, `CompileNative`, `Invalidate`, `EvictIrOnly`, `FlushAll`, destructor), `src/jit/include/brimir/jit/executor.hpp`, `src/jit/src/executor.cpp` (constructor)
- Test: `tests/unit/test_jit_worker.cpp`

**Interfaces:**
- Consumes: `INativeBackend::Prepare/Commit` (Task 1), `CompileWorker` (Task 2).
- Produces:
  - `BlockCache` constructor gains `CompileWorker *worker = nullptr` as its last parameter. `Executor(BackendKind kind = DefaultBackend(), uint32_t nativeCompileThreshold = kNativeCompileThreshold, CompileWorker *worker = nullptr)` passes it through. Not owned.
  - `constexpr size_t kMaxPendingCompiles = 512;` (per cache).
  - `uint64_t CachedBlock::pendingTicket = 0;` (0: no compile pending). It is the ticket of the job submitted for this entry; tickets are unique per cache and encode its generation.
- **Rule (with a worker):**
  - A block's threshold run (the run that calls `CompileNative` today) calls `Prepare` instead, after the same code-cap handling. On success it records `codePages` in the entry at that moment (they are what the prologue compares), submits a job whose ticket identifies this entry and the cache's current generation, and returns the entry still IR-only.
  - At `kMaxPendingCompiles` it does not prepare; it sets `runsUntilNative = threshold` to retry later.
  - A `Prepare` failure counts as today's compile fallback.
  - Threshold 1 (`kNativeOnFirstRun`) and `compileNow` builds stay synchronous, so tests that need native code at once are unaffected.
- **Install:**
  - At the start of `Get`, if `worker->HasResults(this)`, take the results.
  - For each one: if its generation is current and the map entry for its PC is the same entry, still IR-only and still pending, then `Commit`; on success, free the IR and publish exactly as `CompileNative` does today. Otherwise drop it.
  - `Finalize` or `Commit` failure counts as a compile fallback, and the block stays IR-only.
- **Drops:**
  - `Invalidate`, `EvictIrOnly` and the native cap path drop pending entries like any IR-only entry; their results are dropped later by the ticket check.
  - `FlushAll` increments the generation and calls `worker->Cancel(this)`. The destructor calls `worker->Cancel(this)`.
- **Counters:**
  - `uint64_t AsyncCompiles() const` (committed from the worker);
  - `uint64_t AsyncDropped() const` (results dropped);
  - `size_t PendingCompiles() const`;
  - `NativeCompileNs()` now counts emulation-thread time only (`Prepare` + `Commit`, or the synchronous compile).
  - Bench prints them in Task 4.
